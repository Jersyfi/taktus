# DEC-0224 — Secrets are kept in a password manager, for the session and for Taktus

**Category:** NON-BLOCKING
**Mode entry:** M4 (the owner's own accounts and what they hold), M2.5 (needs requests follow from it)
**Raised in:** the session that builds package D, on 2026-10-31, by the owner's message in conversation
**Issue:** none; the owner answered in conversation
**Needed by:** 2026-10-31
**Written after the answer:** the owner stated it in conversation on 2026-10-31; left out of the acceptance rate (DEC-0042).

## 1. What this is about

Until now every credential reached a session or the instance as a file the owner wrote by hand on
the machine: the coding agent's key, the repository token, the keys a needs request asks for.
Each one was a separate step for the owner, and nothing recorded where a value lived or when it
was rotated. The owner now keeps passwords, SSH keys and other secrets in 1Password.

## 2. Why you are being asked

Which accounts the owner holds and what they contain is the owner's own matter. No session can
choose a password manager for the owner.

**Sources checked:** CLAUDE.md §9 (no secret value), `CREDENTIALS.md`, ADR-0028 (needs requests),
DEC-0048 (credentials in CI), DEC-0201 (a tenant creates its own credentials).

## 3. What you must decide

Where secrets are kept, who may read them, and whether Taktus gets an identity of its own there.

## 4. What you need to know to decide

A service account of 1Password reads the items of the vaults it is granted, and writes them if
permitted, with a token of its own. The command-line client `op` uses that token. It can write a
value into a file or hand it to a process without printing it.

## 5. Options

### Option A — 1Password, a service account for the session and one for Taktus (recommended)

### Option B — files written by hand, as before

## 6. What is blocked

Nothing.

## Outcome

**Decided:** 2026-10-31
**Answer:** Option A, in the owner's words: "1password soll für das speichern und lesen von
Passwörtern ssh keys, usw. verwendet werden" (1Password is used to store and read passwords, SSH
keys and so on). This holds for the session, for which the owner holds a service account's key
that is to be stored. "Taktus kann gerne einen eigenes Dienstkonto bekommen" (Taktus may have a
service account of its own). The vault is `Development`.

**Reasoning given:** none beyond the decision itself; one place for every secret, and an identity
of its own for each reader.

**Recorded in:** this pull request.

**What it changes:**

1. **The session** reads a secret through its own service account and only into a file or a
   process. It never prints a value, never reads one into its own output and never writes one
   into the repository, a log or a message. The token of the service account is supplied under
   NEED-0040.
2. **Taktus** gets a service account of its own, separate from the session's, with access to
   what the instance needs and nothing else (NEED-0041). The two never share a token, so either
   can be withdrawn alone.
3. **Needs requests** whose value is a random one the owner only generates (NEED-0037, and the catalogue's signing seed of #658)
   can then be generated by the session straight into the vault. Their steps are rewritten when
   the session's access works, and the owner's part shrinks to granting access.
4. **The product does not change by this decision.** Taktus reads a secret from a file
   (`TAKTUS_<KEY>_FILE`), and a password manager is one way among others to supply that file.
   Whether Taktus should read from a secret store at run time is an architectural question. It
   comes as an ADR with its own issue, with files as the alternative that always stays
   (principle 13).
5. Where the owner's account and the vault are named in detail is outside this public repository.
