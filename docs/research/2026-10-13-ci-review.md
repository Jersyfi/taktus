# CI review of 2026-10-13

The owner asked where development time goes, and how sessions and Taktus's own processes can get
through CI as fast as possible without losing quality. Another project of the owner, developed
entirely by AI sessions, was the reference (`Jersyfi/hubtask`). The method that follows is
ADR-0096; the owner accepted it in DEC-0194.

Raw data and scripts were kept outside the repository. Every figure below names how it was taken.

## 1. Where the time goes in this repository

Data: all 1 127 workflow runs from 2026-09-15 to 2026-10-13, the job and step timings of 148
`ci` runs, the last 100 merged pull requests (#187 to #387), and ruleset 23481185.

- **One `ci` run takes 26–27 minutes since 2026-10-11; on 2026-10-08 it took 6.8.** The required
  check `gates` runs fourteen steps in one job. Median of 30 green runs:

  | Step | Median |
  |---|---|
  | `gate-conformance` (250 tests) | 980 s |
  | `make test` (2 397 tests) | 554 s |
  | lint, types, architecture | 26 s |
  | every documentation and register gate together | under 15 s |

  The conformance suite grew fourfold with the second coding worker (#214) and the ML bench
  (#215). Its fixtures in `tests/conformance/conftest.py` start a fresh worker process for every
  test and pace steps with real sleeps of 0.2 to 0.3 s. Nothing runs in parallel: there is no
  `pytest-xdist` and no timeout.
- **CI runs during 52 % of the time a pull request is open.** 80 pull requests were open 6 530
  minutes in total; a `ci` run covered 3 414 of them. The merge follows the last green run after
  a median of 0.5 minutes. Nobody waits for the owner.
- **44 % of the pull requests' CI minutes re-checked a branch brought up to date.** The ruleset
  requires a branch up to date with `main` (`strict_required_status_checks_policy: true`), and a
  personal repository has no merge queue. 62 of 146 pull-request runs, 1 487 of 3 399 minutes,
  ran on a "Merge origin/main" head.
- **Other waste:**
  - 63 superseded runs kept running, 655 minutes: `ci.yml` has no concurrency group.
  - 18 of 80 pull requests changed only documentation and ran the full suite, 734 minutes.
  - On `taktus/**`, push and `pull_request` checked the same commit 16 times, 214 minutes.
  - No job has a timeout.
- **Flaky tests: about 11 failures in 6 tests.** Issue #360 names three. Missing from it:
  - `test_runner_failover.py:346`, 3 failures;
  - `test_time_triggers.py:109`, a `tenant_pkey` collision;
  - the token-limit test in `test_worker_v1_coding.py:185`.

  Five of the ten failed pushes to `main` failed in a test that had just passed on the pull
  request with the same tree.
- **The secret scan failed three times without finding a secret.** It ends with "partial scan"
  on a commit range, which turns the required check red.
- **Only `gates` is required.** `contracts`, `decisions`, `web` and `description` may be red when
  a pull request merges.

## 2. The merge replay

Question: would `main` have broken if branches were not brought up to date before merging?

Method:

1. For each of the last 100 merged pull requests, take the branch head before its catch-up merges with `main`.
2. Merge that head with `git merge-tree` onto `main` as it stood right before the squash.
3. Compare the result with the tree that landed.

The method follows hubtask's decision record 0083.

| Outcome | Pull requests |
|---|---|
| no catch-up | 51 |
| the identical tree: the catch-up only cost time | 19 |
| a textual conflict: a catch-up would have been needed anyway | 30 |
| a different tree | 0 |

The 30 conflicts are almost all in files many pull requests extend by hand:

| File | Conflicts | Merged automatically beside them |
|---|---|---|
| `docs/decisions/README.md` | 15 | 21 |
| `docs/status.md` | 11 | 27 |
| `docs/architecture/project-structure.md` | 6 | 15 |
| `docs/adr/README.md` | 4 | 6 |
| use cases, e.g. UC-6.10 | 3 | 3 |

DEC-0026 and DEC-0027 already forbid a line every pull request must rewrite. They do not cover
an index or a status paragraph that many pull requests extend.

## 3. Parallel conformance, measured

The four slowest conformance files were run on 2026-10-13 on a 14-core laptop at `main`
4e0f3ab:

- `test_worker_v1_second_coding.py`
- `test_worker_v1_coding.py`
- `test_worker_v1_mlbench.py`
- `test_worker_v1_faults.py`

| Run | Tests | Wall time |
|---|---|---|
| serial | 104 passed | 626 s |
| `pytest -n 8` | 104 passed | 80 s |

The parallel run was 7.8 times faster. All 104 tests passed in both runs, so the fixtures'
isolation holds under parallelism. A GitHub-hosted runner has four cores. A factor near four
there is an inference, not a measurement. The integration tests of `make test` need a database
per parallel worker, so their gain is not measured yet.

## 4. The reference: hubtask

Data: 1 500 `ci` runs from 2026-09-18 to 2026-10-13, 150 merged pull requests, its workflows,
its decision records 0079 and 0083, all read-only.

- **The project:** a Go monorepo with Svelte clients.
- **Throughput:** 647 merges in 58 days, about 11 a day.
- **CI time:** a full pull-request run takes a median 8.1 minutes.
- **Time to merge:** from ready to merge, a median 35 minutes before its decision record 0083 and 11 after it.

Adopted, as ADR-0096 states:

- One required check that always reports. A skipped job counts as passed. On a draft the check is renamed, so a draft never satisfies it.
- Path filters as code, with a test that fails on a path no filter claims.
- One parser selects the checks for the local verification and for CI.
- A draft is verified locally; CI runs when a pull request is ready. A session hook refuses `gh pr ready` without a stamp for the pushed head. hubtask measured 64 % fewer runs.
- No catch-up with `main`, with safeguards:
  - every commit on `main` gets its own full run, never cancelled;
  - a guard in the required check holds pull requests while `main` is red;
  - an automaton runs after CI: it repeats a failed run once and opens and closes an issue "main is red".
- Every job has a timeout, and a test enforces it.
- Each gate is fed a deliberate violation and must go red.

Not adopted:

- **Its nightly run is red 55 % of the time** (25 of 32 runs in September). A run that is always red is no longer read.
- **Its repeat hides flaky tests.** There is no rate and no quarantine.
- **A change anywhere in a language reruns the whole suite of that language.** Taktus's enforced component boundaries allow a finer selection.
- **Its documented settings differ from the repository's real ones**: the actions allowlist and the owner-only merge.
- **It deploys on every merge.** Taktus never deploys itself (ADR-0013 D).
