# Status of `0.3.0` — visibility

Part of `docs/status.md`: how far `0.3.0` has got, checked against the code and the tests.
What the milestone must reach is in `docs/roadmap.md`. Kept current by every pull request that
changes its state.

**A run or a process asked for in the owner's chat is answered there** (#193, `0.3.0`,
ADR-0069). The chat cannot draw a level, so `show run <run>` or `show process <process>` in
the owner's conversation is answered with the level's text equivalent — the one the web app is
handed, with the same states and figures — and the link to the level live in the web app. Only
the owner and whom the owner named are shown anything, only what they may see, and no secret
value (NTC-0147). Proven against the fake chat service; on the installed instance it waits for
NEED-0018 and NEED-0020, like the rest of the channel. `show overview` is answered the same way
with the overview, each area, process and running step, and a link to the web app's root route
(#204, NTC-0148).

**A contribution from a person Taktus does not know is triaged for the owner** (#245, `0.3.0`,
UC-1.9, ADR-0088). On a channel `TAKTUS_TRIAGE` names, an issue or pull request an unknown sender
opens is kept as data, without their account or text, and starts P-05 Triage of contributions
once, acting for whoever registered it. Spam is closed by a fixed pattern or the model's verdict,
nobody asked; a defect or a feature waits for the owner's decision request and is put in its
version, or closed with the owner's answer; nothing is merged and nobody is blocked. Steps may now
run under a condition (`when`) and ask before they act (`ask`). Proven against the fake
repository service and a fake model. The methods are provisional under DEC-0180; the contributing
guide's notice is DEC-0181, and until it is answered the triage is not switched on for this
repository.

**The DevOps review and the product outlook** (2026-10-12). The owner adopted every finding of a
review of the concept for production use, read against the whole range of customers from a person
to an operator hosting Taktus for others (DEC-0187, DEC-0188,
`docs/research/2026-10-12-devops-review.md`), and every proposal of a look at the market
(DEC-0190, `docs/research/2026-10-12-market-review.md`). Both are issues #309 to #354, placed from
`0.3.0` to a new milestone `2.0.0` for operators (`docs/roadmap.md`). Five of them are faults and
leaks for `0.3.0`: a deadlock between two ledger records, listing runs that blocks the process, an
object cache without a bound, cache writes booked too cheaply, and project values as product
defaults (ADR-0092). Migrations run beside the previous release from now on (ADR-0093). The
project's own records follow six working rules (DEC-0189). The deadlock is fixed (#309,
NTC-0201): the ledger's claim on a tenant's chain is its only lock, and every database
connection carries `lock_timeout` and `idle_in_transaction_session_timeout`. Listing runs no longer blocks the
process (#310): `GET /runs` answers a page, the overview counts runs by query, and 2 000 runs of
ten steps each are answered in a twentieth of a second instead of 45 to 57 (ADR-0094, NTC-0202). Cache writes are
booked by their kind in either shape an endpoint reports them, the operator declares the price
kinds an endpoint reports and M-04 holds it to that, and a `429`'s `Retry-After` defers the step
(#312, NTC-0206); the endpoint in use reports no cached input in either shape, and is declared `input,output` (NTC-0208).
The project's values are no longer product defaults (#313, NTC-0205, ADR-0092 amended): the calibration seed,
the guides manifest's path, the chart's output limit, a finding's form and labels, and the
process that turns a change in words into a proposal are each a setting its operator sets. The
project's own instance sets them in its private values (`deploy/k8s/README.md` §2), and
`tests/architecture` fails on a project process, its repository's path or its owner's name in
`src/` or the chart's defaults.

**The CI review** (2026-10-13). One `ci` run takes 26–27 minutes since 2026-10-11, and CI runs
during half the time a pull request is open (`docs/research/2026-10-13-ci-review.md`). The owner
accepted a method of five rings (DEC-0194, ADR-0096): CI checks what changed before a merge and
everything after it, on every commit of `main`, and every commit on `main` will rehearse the
self-development bundles. Phases 1 and 2 are `0.3.0` (#388 to #392); since 2026-10-15 the
ruleset no longer requires a branch to catch up with `main` (NEED-0026). #388 runs the lanes in
parallel under one required check; the index of the ADRs is printed by `make adrs` and stored nowhere, the status keeps a file per milestone and the source tree is printed by `make tree` — the replay of the next fifteen merges found no conflict left in those files (#392; two patterns that remain are #498); a change runs the lanes it touches, a draft none, and a branch of Taktus's app is checked once, on its push (#390); #391 adds the guard that holds every pull request but a
repair while `main` is red, and the workflow that repeats a failed run once, keeps the flake
register as an issue and opens "main is red".

**Every issue of `0.3.0` is closed, and its criterion is not met** (DEC-0209). A process can be
viewed, changed and rolled back from the web app and chat, and a person sees their own share of
the waiting time; creating one from a description (UC-4.1) is planned by no task. DEC-0209 asks
whether "created" moves with UC-4.1 to `0.4.0`.
