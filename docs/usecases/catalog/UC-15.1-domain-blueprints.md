# UC-15.1 — Domain blueprints — departments instantiated from the catalogue

## 1. What must be achieved

The Taktus catalogue holds a **blueprint** per domain of a business — technology, finance,
sales, purchasing and others. A blueprint is a curated bundle that conducts the systems the
organisation already has: which recurring processes the domain has, which connector capabilities it
needs, which autonomy levels are usual, which figures its value balance keeps, and which acts stay
with a person by law. An organisation instantiates a blueprint in dialogue: Taktus asks for the tools
that exist, connects them, and starts at a conservative autonomy level. A blueprint is a template,
not a corset; each instance is adapted to its organisation. Blueprints can be exported, name systems
only by capability, and an instantiated domain is part of reporting, controlling and governance in
full.

## 2. How it is verified

- A blueprint names its processes, the connector capabilities they need, the usual autonomy level of
  each with its reason (ADR-0026), its value criteria, and the acts that stay with a person (UC-15.5).
  A blueprint missing one does not enter the catalogue.
- Instantiation runs as a plan in dialogue (UC-1.2): Taktus asks for the existing tools, binds them
  by capability (UC-1.3), and starts every process at autonomy level 1 or 2.
- No process of an instance runs before the domain has its one named owner (UC-15.5).
- An instance is the organisation's own. A later version of the blueprint is offered to an instance
  as a proposal; it is never applied on its own.
- A blueprint names systems only by capability (ADR-0003). Replacing the accounting or the customer
  system behind an instance breaks no process of it: the removal test (UC-8.9).
- Every process of an instance is in the ledger, the value balance and governance, and the value
  balance can be aggregated per domain.
- A blueprint exports as plain files that can be read without Taktus (UC-8.9).

## 3. Where the boundary lies

**Not a domain system.** Taktus keeps no books and no customer records of its own
(`docs/vision/non-goals.md`). **Not the domains themselves.** Each domain is a deployment under
`blueprints/`; the table of example domains and what stays with a person in each is
`blueprints/README.md`, and the finance domain, UC-15.2, is `blueprints/finance/`. **Not a reviewed legal
catalogue.** The acts that stay with a person are reviewed per jurisdiction before a finance or
personnel blueprint is used (DEC-0029).

## 4. What it rests on

Process bundles (ADR-0011); the autonomy statement (ADR-0026); the adapter obligation (ADR-0003); the
responsibility anchor (UC-15.5); method scaffolds, of which a blueprint is the domain-level kind
(UC-13.2); the two blueprints that exist, `blueprints/dev-orchestration/` and
`blueprints/self-operation/`. Definition `UC-15.1`, new in version 2. The version is `0.7.0`, where the
second domain, systems operation, is instantiated.

**What an accepted decision supersedes in the definition's text.** The definition says blueprints
are in *the open bundle format*. The bundle format exists inside Taktus from `0.3.0`; an open
specification that other orchestrators can read is after `1.0.0` (ADR-0011). What holds now is that a
blueprint leaves Taktus as plain files a person can read without it.

## 5. What is proven so far

Built in ADR-0263. A blueprint missing a part is refused with every finding, and the four
blueprints of this repository enter the catalogue. An instance asks for a tool per capability and
for its owner; nothing is proposed while either is open; every process is proposed at level 1 or
2, and a person commissions it. A later version is offered as proposals and applies nothing.
Replacing the connector behind an instance's capability changes its process and breaks none. The
runs of an instance are counted per domain. A blueprint exports as its own files.

Missing. The value balance per domain: the balance of a process (UC-9.3) is not built, so a
blueprint's value criteria are stated, not computed; only the runs are counted. Governance in
full: the instance names its owner, while the domain's owner across the tenant's governance —
and what holds when the owner leaves — is UC-15.5's domain record, which this instance does not
yet feed. The dialogue is the instance's list of questions, not a plan record of UC-1.2, which is
not built either. The removal test is shown with a stand-in capability, not with an accounting or
customer system of a shipped blueprint.
