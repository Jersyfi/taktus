# UC-10.1 — Runs anywhere, at any scale, on any hardware

## 1. What must be achieved

Taktus works for everyone — a private person as well as a business — and runs anywhere, without being
bound to hosting by its maker: on a home server, in a small company, as a large deployment with high
availability, scaling and several tenants, in any provider's cloud, and in a regulated or state
environment that is cut off from outside networks and hardened.

The execution layer abstracts the hardware there is: ordinary processors, graphics cards, and dedicated
accelerators for artificial intelligence, including classes of processor that do not exist yet. Taktus
recognises the resources available, uses them well for local models, and makes visible which hardware
makes which capability possible.

## 2. How it is verified

- A private person installs Taktus with one command, and an organisation deploys it from a referenced
  description of its infrastructure, kept as code. Both are exercised by an automated test.
- The features are the same in every variant: one release, with configuration as the only difference.
  A test runs the same process, unchanged, in two variants and finds the same steps executed.
- Moving between environments — local and cloud, a graphics card and an accelerator — needs no change to
  a process or an agent, only to configuration.
- Taktus runs with every route to outside networks closed, its models local (UC-8.3).
- The resources an instance has — processors, memory, accelerators — are detected and shown, and for each
  local model it is shown which hardware it needs and whether the instance has it (UC-8.10).
- Taktus needs no service of its maker to run: no licence server, no account, no telemetry sent home.
- No instance runs on infrastructure it administers itself (ADR-0025).

## 3. Where the boundary lies

**Not every platform tested.** Which environments are exercised in continuous integration is the
roadmap's; this use case requires that none is excluded by design. **Not the cluster's operation.** The
infrastructure is run by its operator; Taktus watches what it needs from it (ADR-0031) and does not
administer what it runs on. **Not making a model fit hardware that cannot carry it.** Taktus says what is
missing; it does not promise that every model runs everywhere.

## 4. What it rests on

The business-critical requirements, among them several instances and restart without data loss
(ADR-0013); tenants and instances (ADR-0020); where an instance may run (ADR-0025); Taktus watching the
platform it runs on (ADR-0031); running on own hardware (UC-8.3) and limits that do no harm (UC-8.10);
`deploy/` with its compose file and chart. Definition `UC-10.1`. Filed in `governance`, which holds the
platform's capacity report (NTC-0064). The roadmap names no version; `1.0.0`, where a stranger must be able
to run Taktus without asking, is the session's proposal.

## 5. What is proven so far

**The same release in two variants, with no route outside.** The control plane image of the
checkout runs the shipped first process, unchanged, once with no network at all and its state in
files, once beside a database on a network without a route outside. In both a connection to an
outside address fails, and the same three steps are executed with the same methods
(`tests/integration/test_runs_anywhere.py`, Docker, ADR-0284 §7).

**The hardware, detected and shown.** `taktusctl hardware` prints the processors, the memory
and the accelerators, and for each configured model what it declares in `TAKTUS_MODEL_NEEDS`
and whether this machine has it (`tests/integration/test_hardware_command.py`). Accelerators are
read by kind from the kernel's device classes: a graphics card with its memory, and a device of
the accelerator class, which takes in a kind of processor that has no name yet
(`tests/adapters/platform/test_hardware.py`). Inside a Linux container the kernel's classes are
read; on macOS the accelerators are said to be not observed, never "none". The fit is a rule:
met, missing or unknown per need. Moving a model from a graphics card to an accelerator is a
change of its declaration only (`tests/components/governance/test_hardware.py`).

**No service of its maker.** With nothing configured, no model, connector, telemetry endpoint
or findings intake is named, and the HTTP surface listens on its own machine
(`tests/composition/test_settings.py`). No address in the shipped code, the web app, the compose
file or the chart names a host outside the deployment. The maker's domain appears only as the
namespace of the contracts' schemas. No library whose purpose is to send usage home is a
dependency (`tests/architecture/test_no_service_of_its_maker.py`).

**One command, and infrastructure as code.** The install on one machine creates the first
tenant once (`tests/integration/test_first_start.py`). The install on a cluster from the
operator's values was exercised against stand-ins for the cluster's tools, not on a cluster
(`tests/deploy/test_start_cluster.py`, ADR-0228).

**No instance on infrastructure it administers.** A step or a version naming a credential that
administers the instance's own platform is refused (`tests/governance/test_autonomy.py`,
`tests/governance/test_raise.py`, ADR-0025, ADR-0052).

**What is not shown.** A local model answering while every route is closed is UC-8.3's and not
exercised here. No real graphics card or accelerator was present: the adapter was held to
recorded kernel trees. The two variants ran on one machine with Docker; the chart's variant has
its own target, `make verify-kind`, which installs the chart and runs no process. A model served
by another of the organisation's machines is compared with the control plane's machine
(ADR-0284, *Where this promise ends*).
